# Bounded timezone-correct reminder scheduling design

**Date:** 2026-08-04  
**Status:** Approved for autonomous implementation  
**Tracking issue:** #98

## Product objective

LifeOS can schedule and evaluate workspace-owned reminders at the intended instant, respect each reminder's named time zone and quiet-hours policy, cap delivery frequency, and prevent concurrent scheduler runs from delivering the same reminder twice. This slice provides an in-app delivery port and no email, SMS, push, OAuth, or provider credential.

## Architectural boundaries

The notification capability is an independently runnable `apps/notification-service` workspace package. It has no direct dependency on identity, planning, habit, review, calendar, or AI storage. Callers supply the workspace boundary through the trusted `x-workspace-id` HTTP header; JSON bodies cannot supply or override ownership.

The package is divided into three focused units:

1. `reminder-domain.mjs` owns validation, canonical reminder and outcome records, IANA time-zone projection, quiet-hours evaluation, and bounded retry calculations.
2. `reminder-scheduler.mjs` owns repository and delivery ports, the atomic claim protocol, deterministic batch evaluation, the in-memory reference repository, and the in-app inbox delivery adapter.
3. `main.mjs` owns the bounded versioned HTTP boundary and process bootstrap. It does not expose provider configuration, arbitrary destinations, or credential material.

The initial repository is process-local by design. Its interface is shaped so a later PostgreSQL implementation can replace it without changing the scheduler or HTTP contract. Process restart durability, transactional outbox delivery, external channels, and distributed leases remain follow-up slices.

## Identifier and input contract

- Workspace IDs, reminder IDs, claim IDs, outcome IDs, and delivery IDs are lowercase UUIDv4 strings.
- Reminder IDs are generated by the service. JSON ownership or identifier injection fails closed.
- Titles contain 1–160 Unicode code points, at most 1,024 UTF-8 bytes, and no C0 or DEL control characters.
- Due instants use RFC 3339 and are canonicalized to UTC ISO strings.
- Time zones must be named zones accepted by `Intl.DateTimeFormat`; fixed-offset pseudo-zones and implicit host-local time are not used.
- Quiet hours use exact `HH:mm` start and end values. Equal endpoints are rejected rather than being interpreted ambiguously as disabled or all-day.
- Delivery limits are integers from 1 through 10 per reminder-local calendar day.
- Maximum transport attempts are integers from 1 through 5.
- Scheduler batches are integers from 1 through 100.
- HTTP request bodies are JSON objects of at most 16 KiB with exact allowed keys.

## Time-zone and DST semantics

RFC 3339 represents due instants; the IANA Time Zone Database and ECMA-402 `Intl.DateTimeFormat` project an instant into the reminder's local calendar date and wall-clock minute. Policy is therefore evaluated from actual instants rather than by manually applying UTC offsets.

Quiet hours are a half-open interval `[start, end)`. Intervals may cross midnight. When evaluation occurs during quiet hours, the scheduler searches forward through actual instants in one-minute increments, bounded to 48 hours, and chooses the first instant whose projected local minute is outside quiet hours. This makes spring-forward gaps and fall-back repetitions deterministic without inventing a nonexistent local timestamp.

A daily delivery limit is counted by workspace and the reminder's projected local date. When the limit is reached, the reminder is deferred to the first eligible instant on the next local date; it is not silently discarded.

## Atomic evaluation and retry model

The repository exposes `tryClaimEvaluation`. It synchronously records one UUIDv4 claim token before the scheduler invokes the delivery port. Concurrent runs may list the same due reminder, but only one claim succeeds. Every completion operation must present the matching claim token.

An evaluation has exactly one recorded outcome:

- `delivered`: the in-app delivery port accepted the envelope; the reminder becomes terminal.
- `deferred`: quiet hours or the local-day fatigue limit moved `nextEligibleAt` forward without consuming a transport attempt.
- `failed`: the delivery port rejected the envelope; one attempt is consumed and the reminder is retried with bounded exponential backoff.
- `suppressed`: the configured attempt limit was already exhausted; the reminder becomes terminal without another transport call.

The scheduler never records provider payloads, stack traces, exception messages, cookies, authorization values, or destination addresses. Failure reasons are fixed enums.

## HTTP surface

- `GET /health` returns a credential-free service status.
- `POST /v1/reminders` creates one workspace reminder.
- `GET /v1/reminders` lists workspace reminders in deterministic order.
- `POST /v1/reminders/run-due` evaluates a bounded due batch for the workspace using the server clock.
- `GET /v1/reminder-outcomes` lists bounded workspace outcome evidence.
- `GET /v1/inbox` lists in-app reminder deliveries for the workspace.

Every non-health route requires `x-workspace-id`. Responses use `Cache-Control: no-store`. Validation, not-found, conflict, and dependency failures use bounded RFC 9457-style problem details and never echo untrusted values.

## Testing and quality evidence

Node's built-in test runner executes the real domain, repository, scheduler, delivery adapter, and HTTP handler. The package test command enforces 100% line, branch, and function coverage for all production modules.

Evidence covers:

- RFC 3339 and UUIDv4 validation
- IANA time-zone validation and Unicode/control/byte bounds
- due-time equality and pre-due exclusion
- same-day and overnight quiet hours
- spring-forward and fall-back behavior through actual instants
- per-local-day fatigue limits
- deterministic batch order and hard caps
- concurrent duplicate-claim prevention
- retry-safe transport failures and attempt suppression
- tenant isolation and immutable returned data
- exact HTTP keys, body limits, ownership injection rejection, no-store responses, and credential-free errors

- RFC 3339, *Date and Time on the Internet: Timestamps*
- IANA Time Zone Database
- ECMA-402 `Intl.DateTimeFormat` named-time-zone semantics
- RFC 9457, *Problem Details for HTTP APIs*
- RFC 9110 HTTP method, status, and cache semantics

- distributed scheduler leadership and lease recovery
- reminder update/cancel APIs and user preference UI
